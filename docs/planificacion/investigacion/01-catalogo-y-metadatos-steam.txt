=== PAIR steamdata: Steam catalog & metadata

--- R1 catalog enumeration
SUMMARY: Keyless full list is gone: ISteamApps/GetAppList v1+v2 vanished from Valve's public API listing on 2025-11-13 (SteamTracking diff), breakage reported from 2025-11-16, now HTTP 404; Valve docs say use IStoreService/GetAppList. That endpoint is documented, needs any Web API key (a user key works on api.steampowered.com; partner.steam-api.com needs a publisher key), pages in appid order via last_appid/have_more_results, max_results 50k (default 10k), flags include_games (default)/dlc/software/videos/hardware (no demos/music/mods) and supports if_modified_since deltas. Real output (jsnli daily dump, 2026-10-27): 196,595 games (~20 MB = 4 calls), 63,919 DLC; rows {appid,name,last_modified,price_change_number}; base names, not localized; coming-soon, free and adult-only games included; delisted games excluded; regional SKUs included; churn ~3.3k games/day. A key needs a non-limited account (>= US$5 spent) + Steam Guard Mobile Authenticator; ToU: 100k calls/day, key confidential, licence 'specific to your Application' -> one server-side key; sync needs ~45 calls/day.
Live-tested today WITHOUT key: IStoreQueryService/Query (undocumented) gives up to 1000 ids/call, deep offsets OK, sort=2 = ascending appid, filters released_only/coming_soon_only/type/content descriptors. Totals now: 317,807 store apps; 196,617 games = 133,880 released + 62,681 coming soon; 63,079 DLC; 43,376 demos; 11,595 soundtracks; 2,919 software; 9,674 adult-only. IStoreBrowseService/GetItems (keyless) gives localized names, type, coming-soon/early-access/release date, content descriptors and unlisted:true for delisted games (appdetails still says success:true). SearchSuggestions/storesearch are keyless typeahead fallbacks. No CORS headers -> Steam calls must be server-side. Throttling undocumented (community: ~120 req/5 min/IP). SteamSpy only as popularity signal; PICS is complete but heavy and ToS-gray; SteamDB has no API and forbids scraping.
Plan: keyed GetAppList backbone (games only for MVP) + keyless GetItems/Query enrichment + soft-delete/unlisted tracking + ~1.9 MB (brotli) client-side name index for instant search; keyless Query pass as feature-flagged fallback. RISKS:
- Undocumented keyless endpoints (IStoreQueryService/Query, IStoreBrowseService/GetItems, SearchSuggestions) can start requiring a key or change shape without notice; ISteamApps/GetAppList itself vanished with no dated announcement.
- The key is tied to a personal Steam account: if the account becomes limited (< US$5 spend), loses its mobile authenticator, or Valve terminates the license ('at any time'), the backbone stops; keep the keyless fallback and alerting.
- Per-IP throttling (~120 req/5 min community-measured, multi-hour 429 bans reported); shared serverless/CI IPs may be throttled because of other tenants.
- Delisted games are absent from both GetAppList and Query; games delisted before the first sync cannot be discovered without PICS or third-party dumps, so users won't find them unless appid/URL lookup exists.
- Search noise: ~62.7k coming-soon pages (many TBA for years), ~9.7k adult-only games, placeholder apps and regional duplicate SKUs (e.g. two 'Fallout: New Vegas') degrade results unless ranked and filtered.
- Region effects: Query/GetItems results depend on context.country_code; a US-only context hides some regional SKUs, an ES context may hide others.
- Offset paging on the live Query index can skip or duplicate items when apps are added or removed mid-pass; needs overlap and reconciliation.
- Deltas never report deletions; without a periodic full reconcile, delisted games keep looking available.

--- R2 metadata & media
SUMMARY: The best single source for enrichment is the keyless IStoreBrowseService/GetItems/v1, live-tested on 2026-10-28 with 23 polite requests. Batch size is limited by URL length (about 8 KB), not by a fixed count: 250 seven-digit appids per JSON GET, and 800 passed with input_protobuf_encoded, which returns binary protobuf. context.country_code is mandatory; without it the call returns an empty {response:{}}. context.language localizes text: CJK names, descriptions, review labels and release messages.

One batched call can return, per game:
- localized name and type (EStoreAppType)
- release: Unix timestamps plus is_coming_soon and coming_soon_display (date_full, text_comingsoon or text_tba) with a localized message
- platforms and Steam Deck category
- developers, publishers and short description (basic_info)
- weighted tags (include_tag_count)
- review summary (include_reviews)
- achievement_count, genreids and metacritic (include_extra_details, heavy at 0.4-7 KB per item)
- content descriptors (returned by default)
- asset filenames

Delisted games still come back with success 1 and unlisted:true. Removed or nonexistent ids return success 15 with appid 0, so key results by id. include_best_purchase_option defaults to true; turn it off.

Images: the URL is https://shared.akamai.steamstatic.com/store_item_assets/ + asset_url_format, with ${FILENAME} replaced by the filename. This matches appdetails header_image exactly. Filenames vary (library_600x900.jpg, <sha1>/library_capsule.jpg, portrait.png, none for DLC). Never guess legacy names: they return 404 for new games and stale art for old ones. Use library_capsule as the vertical cover and header as the fallback (present for all 176 sample items). CDN images send ACAO * and a max-age of about 10 years.

CORS: the Steam API and store endpoints send no ACAO, even with an origin= param. A PWA therefore needs a proxy or a static snapshot; Tauri (Rust http plugin) or a server can call Steam directly. API cache hints are short: GetItems 120 s, appdetails 3600 s, tag and category lists no-store.

appdetails takes one appid per call (several only with filters=price_overview, otherwise 400 with body null). It is heavy (42 KB raw), returns localized date strings ('3 AGO 2023'), and has a historic limit of about 200 requests per 5 minutes, so use it only on demand. /appreviews was retired on 2026-10-22 (live: 302); use the GetItems summary, or IUserReviewsService/GetAppReviews for review text. GetTagList (446 Spanish tags, version_hash) and GetStoreCategories (72) are keyless. There is no endpoint for genre names.

Strategy has two tiers:
1. A server or cron job builds a compact snapshot per game: appid, name, year, type, coming-soon flag, cover, t, popularity. That is about 19-48 B per game gzipped, or 3-7 MB for 150k games, for instant local search. It costs about 600 JSON or 215 protobuf calls.
2. When the user adds a game, fetch full flags for that game only (3-10 KB) and refresh it periodically.

RECS:
- Use IStoreBrowseService/GetItems as the only bulk enrichment source. Always send context.country_code (e.g. ES) and a language ('english' for the canonical search name, 'spanish' or 'latam' for display text). Key results by 'id' and skip success != 1.
- Set include_best_purchase_option:false unless prices are shown. Request only include_assets + include_release + include_reviews for the catalog snapshot.
- Batch up to 200-250 ids per JSON GET (stay under ~7.5 KB of URL). Optionally use input_protobuf_encoded with ~600-700 ids per call (needs the SteamTracking .proto files with protobufjs or prost).
- Two-tier data model. (1) A server or cron job builds a compact catalog snapshot per game: appid, english name, alias, year, type, coming-soon flag, cover filename, t, popularity byte, unlisted flag, adult flag. That is about 3-7 MB gzip for ~150k games; the client downloads it once and searches locally for instant results. (2) When a game is added to the backlog, fetch GetItems with full flags (basic_info, release, platforms, assets, reviews, tag_count 10-20, extra_details) for that id only and store the ~3-10 KB result locally.
- The capture path must never wait on the network: saving a backlog entry writes only the appid locally, and enrichment runs in the background.
- Build image URLs only from API data: 'https://shared.akamai.steamstatic.com/store_item_assets/' + asset_url_format.replace('${FILENAME}', file), with the host configurable (shared.fastly.steamstatic.com as alternative; avoid shared.cloudflare, which 301-redirects). Use library_capsule, then header, then a placeholder. Never guess library_600x900.jpg. Lazy-load covers and cache them forever, since URLs change when art changes.
- Ship GetTagList (446 tags) and GetStoreCategories (72) as static per-language JSON and refresh weekly via version_hash. Hard-code a small genre-id table taken from appdetails samples, or show tags instead of genres.
- Filter content descriptors 3 and 4 (adult-only, gratuitous sexual content) by default, with a user opt-in.
- Do not use store /appreviews (retired 2026-10-22). Take the review summary from GetItems; use IUserReviewsService/GetAppReviews only if review text is ever needed.
- Use appdetails only on demand, for localized genre names or highlighted achievements, and parse dates from GetItems timestamps, never from appdetails' localized strings.
- Architecture: because the APIs send no CORS headers, choose either Tauri (calls via tauri-plugin-http from Rust, scoped to api.steampowered.com, store.steampowered.com and *.steamstatic.com) or a PWA backed by a static snapshot on a CDN plus a small caching proxy for on-demand enrichment.
- Throttle all Steam calls to at most 1 request per second with a single worker, exponential backoff and a global pause on 429, and keep a cached-only mode as fallback.

RISKS:
- GetItems, appdetails, GetTagList and the CDN paths are undocumented for public use and can change without notice. Valve already removed ISteamApps/GetAppList and retired /appreviews on 2026-10-22.
- Keyless per-IP rate limits are unknown. A central proxy or cron job puts every request on one IP, so a mass refresh could trigger 429s or temporary blocks.
- Hashed asset paths change when developers update art. Covers cached with old URLs may eventually 404 or show outdated art (not verified), so a re-enrichment path is needed.
- Requesting include_extra_details, full descriptions, trailers or screenshots in bulk inflates responses by 10-30x (up to ~30 KB per item) and could hit unknown response-size or time limits.
- Review counts from GetItems cover Steam purchases only and were reported as 0 for a popular game at least once, so popularity ranking can be noisy.
- About 4% of sampled items are adult-only (descriptors 3/4). Without default filtering they can surface in search results.
- Removed apps (success 15) cannot be enriched at all. Their names and art must come from another source (R1 app list) or a placeholder.
- Steam China (steam_realm 2, country CN) behavior was not tested and may differ.
- Catalog size, and therefore snapshot size and call budget, depends on R1's real game count (150k here is an assumption).
